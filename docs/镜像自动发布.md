# GitHub Release → Docker Hub / GHCR

工作流位于 `.github/workflows/docker-publish.yml`。推送稳定版本标签（如 `v0.6.0`）后，自动检出该标签，运行 Python 和 Node 测试，再构建 AMD64 / ARM64 镜像并推送到 `cachemiao/m3u-studio` 和 `ghcr.io/cachemiao/m3u-studio`。镜像发布成功后，工作流使用仓库自动提供的 `GITHUB_TOKEN` 创建 GitHub Release，并附上该标签的源码 ZIP 与更新记录。也保留“手动创建正式 Release”及 Actions 手动补发入口。

例如发布 `v0.3.5`，将生成 `cachemiao/m3u-studio:0.3.5` 和 `cachemiao/m3u-studio:latest`，GHCR 同步生成相同版本与 `latest` 标签。草稿 Release、预发布 Release 和普通代码提交不会触发镜像发布。标签推送仅接受稳定版本号；工作流创建 Release 不会再次触发构建。标签须采用 `v主版本.次版本.修订版本` 或不带 v 的同类格式。

## 一次性配置

1. 在 Docker Hub 的 Account settings → Personal access tokens 创建用于 GitHub Actions 的访问令牌，赋予 Read & Write 权限，不需要 Delete 权限。
2. 在 GitHub 仓库 Settings → Secrets and variables → Actions → New repository secret 添加 `DOCKERHUB_TOKEN`，值为上述令牌。
3. 令牌仅保存在 GitHub Actions Secret 中，不放入代码、README 或聊天消息。

发布新版本时，先把代码提交到仓库，再创建对应标签和 Release。工作流必须包含在新版本标签所指的代码中。

## 手动补发

Actions → Publish Docker image → Run workflow，输入已有标签（如 `v0.3.4`）。默认只发布版本镜像；仅在需要把该版本设为当前最新版时勾选 `update_latest`。可用于补发或修复失败的发布。

自动发布是否成功，请查看 Actions 运行结果。现有服务器不会因此自动升级；服务器需主动拉取新镜像并重新创建容器，同时保留原数据卷。

## GHCR

工作流通过 GitHub 自动提供的 `GITHUB_TOKEN` 和 `packages: write` 权限发布，无需额外个人令牌。首次发布后在 GitHub 账号的 Packages → m3u-studio → Package settings 中确认可见性为 Public，使用户无需登录即可拉取。

```sh
docker pull ghcr.io/cachemiao/m3u-studio:latest
```

## 发布前检查

1. 在 `CHANGELOG.md` 为目标版本增加 `# v主版本.次版本.修订版本` 标题及说明。
2. 提交源码和对应 README，在本地通过测试后推送分支与稳定版本标签。
3. 到 Actions 查看测试、AMD64 / ARM64 镜像构建与推送结果。只有这些步骤成功后，标签触发的流程才创建正式 Release。
4. 核对 GitHub Release 的源码附件，以及 Docker Hub / GHCR 的版本标签与 `latest`。若工作流失败，不应把镜像或 Release 状态报告为已完成；修复后可重新运行失败的标签工作流。

工作流仅在发布任务内授予 `contents: write`（创建 Release）和 `packages: write`（推送 GHCR）；Docker Hub 使用已配置的 `DOCKERHUB_TOKEN`，无需把凭据写入仓库。
