# 数据库结构与恢复基线

当前结构版本为 `PRAGMA user_version = 1`，与频道发布使用的 revision 无关。现有 v0.6.x 的四张表以前没有设置此版本号，升级时将 0 作为已知基线，事务内检查结构并标记为 1，不重写频道 JSON、账号哈希、账号版本、会话密钥或历史记录。

全新数据目录在同一事务中创建这四张表。失败回滚，不留下部分迁移。重复启动幂等。启动前先检查版本；遇到更高版本会拒绝启动，不尝试自动降级或猜测字段。普通运行与凭据迁移在结构检查成功之后执行。

后续每次变更持久化结构，都必须增加明确的一步迁移、旧版数据样例和失败恢复测试，不能只继续堆 `CREATE TABLE IF NOT EXISTS`。本轮没有新增草稿表或启用服务端草稿。

## 升级和回退

1. 升级前停止服务，备份完整 `/data` 目录，保留当前镜像版本、部署配置和网络策略设置。
2. 在独立数据目录中恢复副本，用目标版本启动，核对登录、频道、台标、发布历史和订阅，再升级正式实例。
3. 回退时停止目标版本，恢复升级前的完整数据目录并使用对应旧镜像。不要让旧镜像直接写入新结构。
4. v0.6.2 及以前的程序没有新版本拒绝保护，因此不能依赖它们自行识别未来结构，必须恢复与其兼容的备份。

配置 JSON 和发布历史不等于完整数据库回滚：它们不包括全部账号、台标文件和部署设置。不要复制正在写入的单个 SQLite 文件来冒充完整备份。技术测试使用 SQLite backup API 复制数据库，并单独恢复台标；用户升级优先沿用停服务后备份整个数据目录的步骤。

测试覆盖：已有结构 0 -> 1 后所有行不变、重复启动、未来版本不写入、迁移失败无部分表，以及备份恢复后登录、历史、订阅和台标可用。这是当前基线，不表示已经证明所有未来迁移都能回退。
